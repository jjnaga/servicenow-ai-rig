## What this instance is

A ServiceNow PDI carrying **two populations laid on top of each other**, and telling them apart is
the single most important fact about working here.

1. **ServiceNow's shipped demo content** — the ACME Corporation group (ACME Americas / EMEA / APAC
   and ~10 country subsidiaries), ~554 users, most of the 2,950 CIs, the OOB catalog and knowledge
   content. Its records carry creation dates of **2005-05-23** and **2012-02-17**. It is scenery.
2. **Nagahama Group (NGB)** — a purpose-built fictional Japanese-Hawaiian conglomerate, authored
   **2026-08-01 → 2026-08-05**, ~95 users on `@nagahama.example`. This is the operating client.
   It has a company tree, business units, cost centres, departments, locations across five time
   zones, 15 operational groups, an incident taxonomy matching its actual lines of business, a
   full P1–P4 SLA set on its own schedules, on-call rotas, and a service catalogue.

The Nagahama layer is **not a sketch** — it is internally consistent to a degree most real
instances are not: 40/40 incident subcategories are dependency-wired, 12/12 routing rules resolve
to real groups, and every SLA resolves to a named NGB schedule.

Layered on top is a **third thing: the rig itself.** This instance is an AI-development testbed.
The same two enhancements have been built **repeatedly and in parallel** by different agents or
runs, distinguished only by table/artifact prefixes (`sf`, `lf`, `b2`, and a scoped variant).
Those duplicates are experiment residue, not an org's architecture — do not read them as intent.

**Practical consequence:** any enhancement you build here targets **Nagahama Group**. Attributing
work to ACME, or reusing ACME groups/companies, means you built against the vendor's demo data.

## 10. Verification notes (traps hit while mapping)

Recorded because each cost a re-derivation, and the codex's rule generalises:

- **An unresolvable FIELD in an encoded query is silently ignored and returns EVERY row.** Control
  test on `task_sla` (60 rows): `zzz_bogus_field=1` → **60**. This produced a false
  "12/12 assignment rules wired" reading against a field (`assignment_group`) that does not exist
  on `sysrule_assignment` — the real field is **`group`**. The conclusion happened to be right;
  the evidence was worthless.
- **Dot-walks, by contrast, ARE honoured here.** Same control: `task.sys_class_name=incident` → 60,
  `=change_request` → 0, `=zzz_nonexistent` → 0, and `group_by task.sys_class_name` → `Incident 60`.
  So the failure mode is *bad field names*, not dot-walking as such. Distinguish the two before
  blaming a query.
- **`sysparm_fields` can return a populated reference field as empty.** `assignment_group` (a
  non-existent field) rendered as `""` under `display_value=all` *and* `None` under
  `display_value=false` — indistinguishable from a real empty value. Fetch the full row when a
  field's emptiness is load-bearing.
- **Creation dates are useless for platform tables on a fresh PDI.** `sys_dictionary` shows
  138,525 / 159,881 rows "created 2026" — that is the Australia install stamping its own metadata,
  not customisation. Filter custom code by **scope**, never by date.
- **`v_plugin.active` is a string** (`active` / `inactive`); a boolean filter returns nothing.
- **Parent-class CI counts double-count descendants** — every count in §3 uses `sys_class_name`.
