# Codex: ServiceNow platform truth

> What it actually takes to have an AI build on ServiceNow without getting silently burned.
> Every finding here was paid for on a live instance and carries the date it was learned.
> Platform behaviour verified across 2026-08-01 → 2026-08-09 on release **Australia** (patch 3,
> build 06-12-2026), SDK **4.9.2** and (entries dated 2026-08-08 onward) **4.10.1**. **Freshness law: re-verify anything load-bearing past ~a quarter** — this platform
> ships two releases a year, and a stale claim in here is worse than no claim.

## WHY this file exists

An AI writing ServiceNow config is not bottlenecked on general platform knowledge — models
already have that. It is bottlenecked on two things a document corpus cannot supply: **what your
instance actually contains** (that is `instance-profile.md`, regenerated by `/sn-map`), and
**which of this platform's behaviours will lie to you** (that is this file).

The second one is the interesting one. ServiceNow fails silent in at least six distinct ways
catalogued below. Every one of them returns success. An agent that trusts its tools ships broken
work confidently; an agent that reads this file first does not.

## WHAT

### Layer 1 — The instance

- **Personal Developer Instances are free** at developer.servicenow.com → Manage → Instances →
  Request. Provisioned in minutes, full admin. The SDK needs **Zurich or later**; a current PDI
  qualifies.
- **~460 in-platform plugins sit inactive and activate HEADLESSLY** via
  `POST /api/sn_cicd/plugin/{id}/activate` plus progress polling (proven: On-Call Scheduling,
  ~3.5 min). That includes serious-org staples — Procurement, the Field Service family, Walk-up,
  Incident Communications, SPM/PPM, Change add-ons. Core Asset Management ships active.
- **Store apps are gated by ACCOUNT CLASS, not by the PDI.** The Store's install flow needs a
  ServiceNow ID tied to a Now Support company account; a developer-program personal ID bounces at
  store login regardless of app price. Signature: Store-delivered apps are not "inactive", they
  are **absent from `v_plugin` entirely**. A real customer account installs the same apps
  trivially — the method transfers, only the personal lane hits this wall.
- **A "fresh" PDI is NOT empty** — expect hundreds of demo users, thousands of CIs, existing
  incidents and catalog items. But the **CSDM layer is empty** (no business applications, no
  service offerings) even with the plugin active. Coexist and attribute (a company reference, or a
  name prefix on tables that have none); **never wipe** — wiping kills your own wiring.
- **Hibernation ≠ reclamation.** Idle instances sleep and auto-wake on **UI** login (~3 min).
  **REST traffic does NOT count as activity** — a full evening of API work still hibernates. The
  symptom is a raw `502 Bad Gateway` on every route with no wake interstitial. Wake lane: dev
  portal → Manage instance → Refresh. It took ~45 minutes once, with a **flapping tail** (bursts
  of 200 between 502s), so treat the instance as up only after **6 consecutive 200s at 15s
  spacing**. **A write that died in a 502 window is IN DOUBT — read it back before retrying.**
- **Do not automate keep-alive logins.** Scripted login simulation to dodge reclamation is
  ToS-gray at best. Log in for real; keep everything rebuildable from source instead.

### Layer 2 — The two lanes

#### Lane A — ServiceNow SDK + Fluent (primary)

Fluent is a TypeScript-syntax DSL (`.now.ts`) compiling to platform metadata XML. It covers 30+
types: tables, business rules, client scripts, script includes, ACLs, roles, UI actions and
policies, catalog items, scheduled scripts, scripted REST, ATF tests, and — from Zurich+/SDK
4.9.2 — flows, subflows, custom actions, and Service Catalog automation.

CLI: `now-sdk auth add` · `init` · `build` · `install` · `transform` (instance XML → Fluent) ·
`download` · `explain` (live API docs — the anti-hallucination tool) · `query` · `pack` · `move`.
**Needs Node ≥ 20.18.** Install the first-party Claude Code plugin:
`/plugin marketplace add servicenow/sdk` → `/plugin install servicenow-sdk@servicenow`.

**Global scope is where real estates live, and it is the right default.** It costs nothing and
buys two things: the app owns no competing default update set, and the cross-scope wall
disappears. `now-sdk init` prompts for Global vs Scoped; a global scaffold writes
`"scope": "global"` in `now.config.json`.

**The delivery model, which surprises everyone:**

- **`now-sdk install` is APPLICATION delivery and captures almost nothing.** Metadata lands in
  `sys_metadata` under the app scope and is versioned in `sys_update_version` against
  `sys_upgrade_history` — the *upgrade* pipeline, not the customer-update pipeline. Measured: a
  full app install with a named update set current captured **4 rows** (2 Flow + 2 Action Type,
  exactly the post-install flow-activation writes) while the table, 8 columns, ACL, script
  include, catalog item, 5 variables, 2 UI policies, 3 policy actions, 2 client scripts,
  notification, and 5 ATF tests captured **nowhere**. 25 artifacts installed, 4 captured.
- **The axis is APP-DELIVERY vs RECORD-AUTHORING, not scoped vs global.** An earlier reading
  blamed scope; it was wrong. A flow is the one class that gets a post-install *activation* write,
  which is an ordinary runtime write and therefore captures normally — generalising from that one
  artifact produced a false law. **One artifact cannot establish a law about an artifact set.**
- **The bridge is the platform's own `Publish to Update Set`, and it drives headlessly.** It is a
  documented feature on `sys_app` whose only logic is
  `GlideAjax('com.snc.apps.AppsAjaxProcessor', sysparm_function='publishToUpdateSet')` — compiled
  Java, no scriptable Glide API, no `now-sdk` command. So the lane is an HTTP call to the same
  endpoint the browser calls. **`/xmlhttp.do` refuses basic auth** (`invalid token`) — it needs a
  real session CSRF token, so: HTTP login → scrape `g_ck` → POST with `X-UserToken` → poll the
  returned `sys_progress_worker`. Measured result: **102 rows, complete, Application Global**,
  0.77 MB payload, every artifact class at its exact expected count. `scripts/sn-publish` is this.
- **You get git AND update sets** — TypeScript source in version control (diffable, deterministic
  keys, delete-by-omission, ATF as source, rollback contexts) *and* one named complete promotable
  update set. Do not build a custom transport; this fork is closed.
- **For genuine out-of-app REST authoring**, the mechanic is the session preference, not the
  scope: `sys_user_preference(name=sys_update_set)` decides where captures land. Create a named
  set → make it current → work in it. There is **no per-request override**, so concurrent agents
  sharing a user race each other: **one API user per concurrent agent.**

**Lane A scars, each measured:**

- **GLOBAL SCOPE SILENTLY DISCARDS UNPREFIXED DICTIONARY COLUMNS.** A `sys_dictionary` insert
  whose `element` lacks `u_` returns **HTTP 201 and creates nothing**. Probed both ways on a live
  table: `zz_probe_bare` → 201, **0 rows**; `u_zz_probe_prefixed` → 201, **1 row**. Columns that
  were legal in a scoped app (which supplies its own prefix) **all vanish** when ported to global —
  the installer prints success, `sys_update_version` records every app file as `current`, and the
  table comes up carrying nothing but its `sys_*` fields. ATF passes, because the tests query by
  column name and there is nothing to query. **Law: after any table install, read `sys_dictionary`
  back and count.** No other gate can see this.
- **The installer does NOT materialise `Table({userRole, createAccessControls})`.** The built
  `dist/` carries no role or ACL XML — only a placeholder reference that installs as a **dangling
  reference**, and the table arrives with **zero ACLs**. Under `glide.sm.default_mode=deny` that
  makes it admin-only and invisible to every real user. Fix: author `Role({name})` and
  `Acl({type:'record', table, operation, roles})` explicitly in source. That works, needs no
  security_admin elevation, creates the role exactly once on upgrade, and the install loader
  repairs the dangling reference by name.
- **SDK 4.10.1 EXTERNAL ROLE REFERENCES NEED `Now.ref`, NOT A BARE NAME** (verified 2026-08-08).
  `Role.containsRoles: ['canvas_user']` hashes the literal as a new deterministic identity; it does
  not bind the existing platform role. Use `Now.ref('sys_user_role', <live sys_id>)`, inspect the
  material INSERT/UPDATE XML, then read the installed role-containment row back.
- **REFERENCE-TYPED DATA PILLS DO NOT CROSS THE CUSTOM-ACTION BOUNDARY in SDK 4.9.2, in either
  direction.** Same flow, same run: boolean, integer, and string pills delivered perfectly; only
  reference pills vanished. *Inbound*, the documented Service Catalog trigger pill reached the
  action's script as something `String()` could not turn into a sys_id, so `GlideRecord.get()`
  missed and the flow died. *Outbound*, the script computed the correct sys_id and the calling
  flow's condition on that reference output **still evaluated EMPTY**, silently taking the
  fail-closed branch — i.e. it read as correct business behaviour, which is what makes it
  dangerous. Fix: coerce defensively inbound (`getUniqueValue()` → `.sys_id` → `String()`), and
  **mirror every reference output as a string column** and have the flow consume the string.
  Re-test on the next SDK bump before trusting a reference pill.
- **By-name placeholder emission is safe for REFERENCE fields and BROKEN for name-carrying STRING
  fields.** The build emits `<field name="human_name">{placeholder_sys_id}</field>`. On a real
  reference field the loader resolves the `name=` hint. But `sc_cat_item_producer.table_name` is a
  **string** holding a table NAME — the loader has nothing to resolve, writes the raw sys_id, and
  **every submit dies as an empty HTTP 500**. Trigger: passing a `Table()` object where the API
  says "a table name string or a `Table()` definition" — the documented option is the broken one.
  **Law: for any field that stores a NAME, pass the literal string, and grep `dist/` for
  `name="…">[0-9a-f]{32}<` before every install** — one sweep catches the whole family.
- **A NEW same-project table cannot be read off a Flow trigger** via
  `params.trigger.current.<field>`: dot form fails TypeScript's
  `noPropertyAccessFromIndexSignature` (the generated types are not visible to the flow at build
  time) and bracket form is rejected by Fluent's own `dataPill` macro. **Working fix: a self
  `lookUpRecord` on the trigger's own record, then `.Record.<field>`.** Costs one flow step.
- **SDK build output is NOT byte-reproducible.** `--frozenKeys` does not cover placeholder sys_ids
  for by-name references, and they regenerate per build without appearing in `generated/keys.ts`.
  **"SHA-pinned" means the exact zip — never rebuild between pin and install**, or you can ship a
  different role sys_id and duplicate the role. Two corollaries: `now-sdk pack` **CLEARS
  `target/`** (six pinned artifacts vanished in one session), and `install` **re-zips**, so a
  post-install checksum never matches its own pre-install pin. The durable fingerprint is the
  **source-tree digest**.
- **A DRAFT FLOW CAPTURES A SHELL.** Before activation: snapshots empty, **zero
  `sys_hub_trigger_instance` rows in the database** (the trigger lives in the designer's unsaved
  state), payload 13 KB with no table binding. After activation: snapshot written, payload 33 KB,
  graph present. **Never ship a flow in an update set without publishing it first — the row will
  be there, look right, and carry nothing executable.** Also, a flow with a trigger but no actions
  **cannot be activated at all**, so "add one action" is a hard prerequisite.
- **`CatalogUiPolicy` and `CatalogClientScript` default `global: true`** in SDK 4.9.2 — an
  unscoped policy applies to EVERY catalog item on the instance. Set `global: false` explicitly,
  always.
- **The SDK upgrade lane cleanly DELETES artifacts removed from source** — delete-by-omission is
  safe (verified: a dropped variable and client script left zero orphans).
- **A `Table({augments: ...})` CAN LOG A HARMLESS `Skipped Error` FOR TABLE DOCUMENTATION**
  (SDK 4.10.1, verified 2026-08-08). The loader emitted the existing table-level
  `sys_documentation_<table>__en`, then skipped it because the coalesced row already existed. Never
  wave the counter away: open the exact upgrade detail and read the preserved live label plus all
  intended augmented fields. Only that combined receipt distinguishes a benign coalesce from a
  partial install.
- **UI PAGE CDATA MARKERS BREAK UNDER JELLY EVEN WHEN THE APP SEEMS TO WORK** (verified 2026-08-08).
  A closing `//]]>` was split into `//]]` plus a bare `>` inside the script, raising a syntax error
  on every load while the module still rendered. Omit HTML-era CDATA markers from SDK UI Pages and
  require a zero-page-error browser pass. Scripted REST browser clients also receive the outer
  `{result: ...}` envelope; unwrap it before checking an inner application receipt.
- First install writes a **`sys_rollback_context`** — an undo path exists even at v0.0.1.

#### Lane B — raw REST (secondary)

Config records are table rows: `sys_script`, `sys_script_include`, `sys_script_client`,
`sys_ui_policy`, `sc_cat_item` + `item_option_new`, and everything in ITSM. All POST-able via
`/api/now/table/<table>`.

- **THE auth gotcha every new instance has.** Fresh instances ship the basic-auth restriction
  **enforcing** (`glide.authenticate.basic_auth.restriction.enforce=true`, with an enforcement
  date set days after provisioning). REST basic auth then **401s for any account without the
  allow-list role `snc_basic_auth_api_access`** — while UI login keeps working, which makes it
  look like a password problem. It is not. Grant the role. **Every per-agent API user needs it.**
  Note the role covers `/api/now/*` **only, never UI endpoints** — that bites again later.
- **Session-token bridge:** when locked out of REST, an authenticated browser session can drive
  `/api/now/*` with header `X-UserToken: <window.g_ck>`. That is how you bootstrap the role grant.
- **Transport is the CI/CD API**, not raw XML:
  `/api/sn_cicd/update_set/{retrieve,preview,commit,commitMultiple,back_out}`, plus `app/install`,
  `plugin/activate`, `instance/scan`. Requires role `sn_cicd.sys_ci_automation`. The native list
  "Export to XML" lacks the `sys_remote_update_set` wrapper and will not round-trip.
- **`export_update_set.do` may be unavailable.** Escalation ladder, all tried: REST basic auth →
  401 (the allow-list role is REST-only); browser session → 401; session + `X-UserToken` → 200 but
  an empty body (it streams a download); Playwright `expect_download` → the event never fires.
  What works: `sys_update_xml_list.do?sysparm_query=update_set=<sys_id>&XML` in-session, which
  returns well-formed XML rooted at `<xml>` with **no `sys_remote_update_set` wrapper** — an
  evidence artifact, not a transport. **Do not hand-fabricate that wrapper** (tried; malformed).
- **Removing a table from Fluent source removes its BEHAVIOUR, not its SCHEMA** (measured
  2026-08-09, SDK 4.10.1). Deleting a `Table({...})` emits `deleted: true` tombstones into
  `generated/keys.ts` — 68 of them in the measured case, one targeting `sys_db_object` — and
  `now-sdk install` honours them for ACLs, UI actions, business rules and notifications (all
  verified 0 after install) but **not** for the `sys_db_object` row, **not** for a column removed
  from an augmented table, and **not** for the rows. The result is an orphaned table holding live
  data with every ACL stripped off it, while the repo reads as though it is gone. **Verify
  `sys_db_object` and `sys_dictionary` directly after any table removal, and drop the physical
  table as a separate human-authorized step.** A clean build, a successful install, and the
  presence of tombstones are all worthless as evidence of removal.
- **Background scripts:** there is no official REST for `sys.scripts.do`. The blessed equivalent
  is **`sysauto_script` (Scheduled Script Execution)** — an ordinary table, Table-API creatable,
  a first-party Fluent type. **⚠ Verify it actually ran.** On a PDI (2026-08-05) a job created
  active, queued by its own `sys_trigger` row (`trigger_type=0` Run Once, `state=0` Ready,
  `next_action` in the past), with the scheduler demonstrably running other jobs, **never
  executed** — no row written, no `gs.log` output, after 40s. The trigger stays Ready and looks
  identical to one that completed. If you use this lane, prove execution with a log marker before
  you depend on it. (An *inactive* job is skipped silently while its trigger is still consumed —
  that one is at least explicable.) **UPDATE 2026-08-09: this failure is confined to the ON-DEMAND
  Run Once path. A `run_type=periodically` job fires exactly on schedule** — verified by log marker
  with the trigger's `next_action` advancing by one period. Prefer periodic; the log marker stays
  mandatory either way.
- **Tables that refuse REST writes by ACL** — treat a 403 here as governance working, not as a
  puzzle to route around: `sys_number` (403 with an **empty body**);
  `std_change_record_producer` (standard changes must arrive through the Standard Change Proposal
  workflow — an agent must not be able to mint its own pre-approved changes);
  `sys_variable_value` (accepts INSERT, refuses UPDATE and DELETE, so a half-written ATF step can
  be neither corrected nor cleaned over REST).
- **READS are refused too, and admin is no exemption.** `sys_store_app` returns **403 "Failed API
  level ACL Validation"** to an account holding `admin` + `snc_basic_auth_api_access` (2026-08-08,
  Australia PDI) — so **store-app inventory is not reachable over REST at all**, and a mapping or
  audit pass must either observe it in the browser or declare it unmeasured. Do not read a read-403
  as a broken credential; the smoke test passing while one table 403s is the signature.
- Scope of a created record can silently follow the API **session's** scope rather than the
  payload — pin it explicitly and read back.
- Rate planning: ~25k requests/hour/user, ~10 concurrent threads per node. A single-node instance
  hits **concurrency** first — keep agent parallelism modest.

### Layer 3 — Grounding without a RAG

Do not build a document RAG. Four sources, in priority order:

1. **Live instance introspection is primary ground truth** — `sys_db_object`, `sys_dictionary`,
   `sys_choice`, `sys_properties`, the role and ACL tables, and existing artifacts as style
   examples. No corpus encodes what YOUR instance actually contains; the instance does.
   ServiceNow's own AI-agent guidance says it outright: verify column names by querying
   `sys_dictionary` before writing tools.
2. **On-demand versioned docs** — `github.com/ServiceNow/ServiceNowDocs` is the full corpus as
   markdown with an `llms.txt` index, **branch-per-release** (pin the branch to your instance's
   release), built precisely because docs.servicenow.com is a JS SPA agents cannot parse. Recipe:
   fetch `llms.txt` → resolve the topic → fetch that one file. Clone it to `vendor/`.
3. **`now-sdk explain`** for Fluent — a young DSL with little training data, and therefore the
   hallucination hotspot. The SDK also ships first-party Claude Code skills.
4. **Parametric knowledge for the decade-stable core only** — classic GlideRecord/Glide APIs, OOB
   table families. Drift concentrates at new and version-gated edges.

### Layer 4 — Verification: where this actually lives or dies

**The headline, from a real run: seven installs, five defects, ZERO caught by the installer.**
Every one printed success — `Installation completed`, HTTP 200, `Flow activation complete: 3/3` —
while leaving the instance wrong. Read-back caught three; runtime caught two. **The verification
stage is not ceremony on this platform; it is where the work is.**

- **GlideRecord fails SILENT on hallucinated field names** — an invalid query returns ALL records
  with no error. Prefer fail-loud GlideQuery for generated queries; read back every mutation.
- **ACL inheritance is the silent-write law in security form.** Table-level ACLs are **not
  sufficient on a Task-derived table**: field-level evaluation walks UP the hierarchy, so with no
  `<your_table>.<field>` rule the inherited `task.<field>` rule decides — silently. Cost: a record
  producer inserted its record fine while `current.setValue('work_notes', …)` **vanished with zero
  `sys_journal_field` rows and no error**, because `task.work_notes` requires `itil`/`task_editor`.
  Counter: after granting table access, **write one field and re-GET `sys_journal_field`**. Fix
  with a field-level ACL (more specific wins), never by granting `itil` to a requester population.
- **DICTIONARY `read_only` OUTRANKS A CORRECT FIELD ACL FOR SECURE/API WRITES** (SDK 4.10.1,
  verified 2026-08-08). `GlideRecordSecure.canWrite()` stayed false for runner fields until the
  dictionary flag was removed; least privilege belongs in the specific runner field ACLs. And for
  Task journals, `setValue('work_notes', text)` can update the parent yet create zero journal rows;
  direct assignment worked. Always read `sys_journal_field` back, not only the parent record.
- **Empty result ≠ success.** Check the worker user's read rights explicitly before believing a
  zero.
- **ATF, headless, is the CI gate.** Author tests in Fluent; run via
  `POST /api/sn_cicd/testsuite/run` → poll `/api/sn_cicd/progress/{id}` (`status_label` DOES
  populate here: Pending → Running → Successful) → `/api/sn_cicd/testsuite/results/{id}`. A suite
  of 3 server-side tests runs in ~10 seconds. House rule: **no test, no hand-off.**
- **ATF STEP SUCCESS IS NOT WRITE PROOF** (Australia/SDK 4.10.1, verified 2026-08-08). RecordUpdate
  can report success after ACL stripping; assert `GlideRecordSecure.canWrite()` and re-read with an
  independent record. Conversely, an intentional unique-index error still fails a test with
  `failOnServerError=true` even when caught. Bank that red receipt once, then use non-error
  count/idempotency assertions for the durable suite.
- **Granting an application role auto-adds inherited roles.** Read back the user's FULL role list
  after a grant and report the extras rather than being surprised in a security review.

### Layer 5 — What a run costs

Measured across four real enhancement runs on two different model families (2026-08; re-derive
before trusting — model pricing and cache economics move faster than the platform does).
**98–99% of every run is cache read** —
you are not paying a model to think, you are paying it to **re-read**. That is what makes this
cost engineerable rather than fixed.

`total input billed = Σ(context at each turn) = turns × mean context`. Verified to the token
against an actual bill. Two consequences:

- **Cost is quadratic in verbosity.** The agent's own output re-enters as input on every later
  turn. In one measured run the mandated read-in (this codex + CLAUDE.md + the loop contract +
  the instance profile) was only **~11% of mean context**; the other 89% was accumulation.
- **Idle polling is the most expensive thing an agent can do.** At high context every turn costs
  the same whether it builds something or runs `ls`.

Levers, by measured impact: **phase-checkpointing** so context sawtooths instead of climbing
(3–5×, no quality cost — the loop's own gates are the natural checkpoints), cutting output
verbosity (1.5–2×), batching trivial shell calls (~1.3×). **Trimming the read-in is the worst
lever** — it is ~11% of context and it is the grounding. Dropping ATF is worse: a few percent of
cost to remove the verification stage that caught five defects in a single seven-install run
(Layer 4).

**Two honest caveats.** Everything measured is **greenfield** — cost scales with mess, and a
long-lived instance is unmeasured. And a cheap model tier matched an expensive one on deliverable
surface for a moderate enhancement while writing **fewer tests**; the expensive tier bought better
test design and found a novel platform defect. Match tier to stakes, and never let a cheap tier be
the only reader of a novel problem.

## HOW

### Platform findings — the working list

*Everything below returns success while doing the wrong thing. That is the theme.*

**Silent-discard family** (the platform's signature failure mode):

- **Choice values.** Writing a value that is not an **active** `sys_choice` returns **HTTP 200**
  and silently keeps the field's prior value. Hit three times in one build: a fresh instance ships
  several Asia time zones **inactive**, so every Asia location came back blank while US and Europe
  took; and inventing criticality labels silently stamped **every** service "not critical" — which
  would have stamped *not critical* on a tier-1 business service. **Validate against `sys_choice`
  before any bulk write — use `sn choices <table> <field>`, which already encodes the correct
  filter.** Do not hand-roll the query: a bare `^inactive=false` is BLIND to choice rows installed
  by a scoped app (they store NULL, and the Table API renders that NULL as `"false"` in the
  response, so the data looks right while the filter matches nothing). An empty result then trips
  the rule directly below and aborts a write that was fine.
- **A field with no choice list of its own may still be validated — find the field it mirrors.**
  One field had ZERO `sys_choice` rows, so validation had nothing to assert and passed; the server
  then silently discarded the value anyway. The real list lived on the field it mirrors. **Treat
  "no choices found" as *unverified*, never as *anything goes*.**
- **Read-only fields are silently dropped.** `cmn_rota_member.roster` is `read_only=true` in
  `sys_dictionary`, so the Table API accepts the insert, returns 200, creates the row, and leaves
  the field empty — 10 orphan rows were the proof. **Check `sys_dictionary.read_only` before
  writing a field, not merely that the field exists.**
- **`max_length` truncation silently breaks upsert keys.** A 45-character name into a
  `max_length=40` field is truncated on insert, so the key query built from the full string never
  matches and a **duplicate is created on every run**. Build keys through a length-aware helper.
- **Unprefixed dictionary columns in global scope** — see Layer 2. HTTP 201, zero rows.

**Query and counting traps** (these poison your *verification*, which is worse):

- **An UNRESOLVABLE FIELD REFERENCE in an encoded query is silently ignored — the clause drops and
  you get EVERY row.** A bad dot-walk returned all **437** rows instead of the intended 31, and in
  a read-back that reads as spectacular success. **NEAR MISS from the same bug:** a cleanup query
  dot-walking a nonexistent path matched every row on the instance and offered **ServiceNow's own
  ATF data** for deletion first. Only an ACL stopped it. **Never drive a destructive operation
  from a filter without first proving the filter narrowed the set.**
  - **REFINED 2026-08-08 (`/sn-map`, Australia): the trigger is UNRESOLVABILITY, not dot-walking.**
    A dot-walk that *resolves* is honoured normally; a **bare field name that does not exist on the
    table** drops exactly the same way. Control-tested on `task_sla` (60 rows):
    `task.sys_class_name=incident` → 60, `=change_request` → **0**, `=zzz_nonexistent` → **0**, and
    `group_by task.sys_class_name` → `Incident 60` — dot-walks work. But `zzz_bogus_field=1` →
    **60**. Reading the old entry as "dot-walks are the risk" is what let this bite: a filter on
    `sysrule_assignment.assignment_group` (a field that does not exist — the real one is `group`)
    returned all 12 rows and was recorded as "12/12 rules wired". The claim was accidentally true
    and the evidence was worthless. **Suspect your field NAMES first, and check `sys_dictionary`
    (hierarchy-aware) before trusting any count.**
  - **The cheap proof, worth making reflex: run a deliberately-bogus-field probe against the same
    table.** `sysparm_query=zzz_bogus_field=1&sysparm_count=true` — if it returns your full row
    count, the filter engine is dropping unknown clauses and *every* count you just took from that
    table is suspect. One extra call converts "this number surprised me" into a decided question.
- **INDEX METADATA IS NOT WHERE YOU LOOK FOR IT, AND THE PLATFORM RENAMES YOUR INDEX**
  (2026-08-09, Australia/SDK 4.10.1). A Fluent `index: [...]` declaration becomes a **physical
  database index only** — no `sys_index` row, no `<index>` element in the stored `sys_dictionary`
  update payload, nothing in `v_index_creator` (which returns zero for every table, including
  `incident`). Read them from **`v_db_index`** (label "Database Indexes"), filtering its **string**
  field `table_name`, **through the list processor** — `v_db_index_list.do?sysparm_query=table_name=<t>&XML`
  — because it is virtual and the **Table API returns 0 rows for it even for `incident`**, so a
  REST zero here is meaningless. Three traps ride along: (1) **the declared index name is
  discarded** — the physical index is named after its **leading column**, disambiguated `_2`, so
  verifying by name finds nothing and reads as a failed install; **verify by column tuple**;
  (2) `sys_index` carries both `logical_table_name` (string, label "Table") and `table`
  (**reference**, label "Reference Table"), so filtering table *names* against the reference column
  silently returns zero — a wrong-*typed* field, which the bogus-field probe will NOT catch because
  the clause resolves; (3) **a Task-derived table has no indexes of its own** (its rows live in
  `task`) and **no read-only surface exposes an index's unique flag** — `v_db_index` has no unique
  column — so uniqueness must come from `sys_dictionary.unique` (column-level only) or a functional
  proof.
- **ATF ROLLBACK POISONS EVENT/NOTIFICATION EVIDENCE** (2026-08-09). Every event raised inside a
  test points at a record ATF then deletes, so the event lands in `sysevent.state=error` and
  generates no email. Measured on one app: 27 of 34 events, **100% of them resolving to a
  now-missing record**. Before reading an error count as a defect, resolve each event's target and
  separate test-raised from runtime-raised. Related: a notification whose only recipient is the
  acting user generates nothing when `sendToCreator: false` — correct behaviour that reads exactly
  like a broken notification.
- **`sysparm_fields` silently omits fields that do not exist** — so a response missing a column
  means "no such field", not "empty value". **The practical hazard (2026-08-08): a generic row
  printer erases the distinction.** Any `row.get(field)` helper renders an *omitted* column
  identically to an empty one — `""` under `sysparm_display_value=all`, `None` under `=false`. A
  populated reference field therefore read as blank across a whole table sweep. **When a field's
  emptiness is load-bearing, fetch the full row without `sysparm_fields` and look at which keys
  actually came back.**
- **Counting a parent CI class double-counts its subclasses.** Scope with `^sys_class_name=<class>`
  for a true per-class count.
- **`sn choices` / choice lookups are not hierarchy-aware.** `sc_req_item.state` has no choices of
  its own (they live on `task.state`); an empty result can mean "walk up the hierarchy", not "no
  choices". Same for fields: `incident.state` lives on `task`.
- **`v_plugin.active` is a STRING** (`active`/`inactive`), not a boolean — `^active=false` returns
  nothing, silently.
- **`sys_created_on` DOES NOT SEPARATE CUSTOM WORK FROM PLATFORM METADATA — the release install
  stamps its own rows with the provisioning date** (2026-08-08, Australia PDI). Measured:
  `sys_dictionary` reported **138,525 of 159,881 rows "created 2026"**, which reads as a
  catastrophically customised instance and is in fact the Australia install writing its own
  dictionary. Same distortion on `sys_choice` (16,431/20,423), `sys_security_acl` (3,651/45,659),
  `sys_script` (161/6,172). **Filter custom code by SCOPE (`sys_scope`, `sys_app`), never by date.**
  The inverse holds and is genuinely useful: on *business* tables (`sys_user`, `core_company`,
  `cmdb_ci`, `cmn_department`) creation strata cleanly separate vendor demo data from authored
  content — ServiceNow's demo seed carries **2005-05-23** and **2012-02-17**, so anything else is
  yours. **Date-stratify DATA; scope-filter METADATA.**

**Data-integrity laws** (learned by creating duplicates):

- **An upsert key must be a deterministic natural key independent of anything derived at insert
  time.** Keying users on `user_name` while also uniquifying `user_name` against existing users
  defeats convergence: the population **doubles every run**. Key on something derived purely from
  the entity (e.g. email).
- **Never retry a POST.** A Table-API POST that succeeds server-side but times out client-side is
  replayed by a naive retry and inserts the row twice. Restrict retries to idempotent methods.
- **`upsert` ≠ converge.** Query-before-insert guarantees *existence*, never *content* — later
  edits silently no-op on re-run. Use insert-or-PATCH wherever the payload is the spec.
- **Spec-driven seeders need a declarative stale sweep** — renaming a record leaves its
  predecessor behind. Retire prefixed rows absent from the current spec, in the same pass.
- **Asset ↔ CI is reciprocal — do not create both sides.** Core Asset Management auto-creates an
  `alm_hardware` asset for every CI inserted with a `model_id`; inserting your own then aborts
  with HTTP 403. Create the CI, then **PATCH the auto-created asset**.

**Catalog and portal:**

- **A failing record-producer submit returns an EMPTY HTTP 500 — the real error exists ONLY in
  `syslog`.** The OOB `submit_producer` wraps the call in a try/catch that rethrows as
  `ServiceError("Invalid Request")`, so the body carries empty strings and the portal UI just
  sits there. **Always pull `syslog` (`level!=0`, newest first) on any catalog failure before
  theorising.** The portal's own button hits the same endpoint, so an API repro is faithful.
- **`use_dynamic_default` + `dynamic_value_dot_walk_path` does NOT render in the Service Portal.**
  Authored correctly and read back correct — the field is simply **blank on the form in every
  order**. Derive the value server-side and treat the variable as display-only. Only browser
  evidence can see this; no read-back and no ATF can.
- **`g_form.getReference()` in Service Portal returns no `manager`** — a manager auto-fill script
  "runs perfectly" and displays a false "(no manager recorded)". Same family: derive server-side.
- **A mandatory catalog variable with no value cannot be hidden by a UI policy** — for anything
  progressive disclosure hides, mandatory belongs on the **UI policy**, not the variable.
- **Role-less record ACLs are a design tool:** under `default_mode=deny` a lookup select box
  renders EMPTY for ordinary users unless a read ACL grants row access. A condition-only ACL with
  **no** role requirement is the load-bearing fix.
- **Driving catalog forms with Playwright:** Service Portal variables expose
  `#sp_formfield_<name>`, but reference and choice variables are **select2-wrapped, so
  `page.select_option()` silently no-ops** — the model keeps its old value and the mandatory check
  blocks submit with no visible error. Use `#s2id_<field id> .select2-choice` → click → type →
  Enter for references, click `.select2-result-label` for choices, and **read
  `#sp_formfield_<name>.value` back before submitting.**

**ATF, authored programmatically:**

- **ATF ships DISABLED** — `sn_atf.runner.enabled=false`. Set it true before any run.
- **Step inputs are NOT on `sys_atf_step.inputs`** (that field is empty on every OOB step). They
  live in **`sys_variable_value`**: `document='sys_atf_step'`, `document_key=<step sys_id>`,
  `variable=<atf_input_variable sys_id>`, `value=<value>`.
- **THE RACE THAT COSTS AN EVENING: inserting a `sys_atf_step` instantiates its blank input rows
  ASYNCHRONOUSLY.** Writing inputs in the same pass lands your row first and the platform's blank
  second, leaving **two rows per variable** — and ATF reads the blank one, failing with "Table name
  was not specified" while the record list looks fully populated. Fix: **two phases** — create
  tests and steps, then after a settle delay, per (step, variable), delete every row and insert
  exactly one.
- **Server-side steps only for headless runs.** Record Insert / Query / Update / Validation
  execute server-side; **form steps require a browser-based client test runner** and will not run
  through the CI/CD API. A suite of form steps is impressive and unrunnable in CI.
- **Verified `assert_type` values:** Record Query → `records_match_query` /
  `no_records_match_query`; Record Insert → `record_successfully_inserted`.
- **`sys_atf_test_result` rows accumulate across re-runs** — read the LATEST per test, or stale
  failures mix into the current run and a green suite reads red.
- **`/api/sn_cicd/testsuite/results/{id}` wants the suite-RESULT sys_id, not the progress id.** It
  arrives as `links.results.id` in the progress payload but is populated only once
  `status_label=Successful` — break out of the poll on the first status flip and it is not there.

**Impersonation and evidence:**

- **Impersonation drives headlessly** — `POST /api/now/ui/impersonate/{sys_id}` with
  `X-UserToken` → 201. Footguns: the plausible `/api/now/ui/impersonate/user` form returns 400;
  **`/logout_impersonate.do` does NOT end an impersonation** (screenshots were captured as the
  wrong identity before this was caught) — use `/logout.do` plus a fresh login; and the session is
  browser-profile-wide, so verify identity with `/api/now/ui/user/current_user` before EVERY
  capture. The platform stamps its own audit line naming the impersonation — **that line is
  disclosure; quote it rather than hiding behind it.**
- **Full-page screenshots capture the browser's own password bubble, including saved personal
  logins.** One capture came out showing an unrelated personal credential. **Review every
  screenshot before it enters a package**, and avoid a fresh login immediately before a capture.
- **CI/CD plugin-activation progress never populates `state`** — it stays null while
  `percent_complete` climbs to 100, so polling on `state` reports a false TIMEOUT for work that
  finished. Treat 100% as terminal and let the read-back be the verdict.

**Miscellaneous truths worth the line:**

- **`glide.buildname` is NOT reliably present** in `sys_properties` (absent on a fresh Australia
  instance, 2026-08-05) despite being widely cited; `glide.buildtag` is absent too.
  `sys_upgrade_history` carries app versions, not the release family. **CORRECTED 2026-08-08: a
  dependable REST-only release probe DOES exist — `glide.war`**, which returned
  `glide-australia-02-11-2026__patch3-05-25-2026_06-12-2026_1106.zip` — release family **and**
  patch level **and** build date, from one `sys_properties` read. Prefer it over "let the SDK tell
  you" and over guessing; it is also what pins the `vendor/ServiceNowDocs` branch. (The earlier
  "no dependable probe" line was written after probing only `buildname`/`buildtag`.)
- **`contract_sla.duration` is an epoch-anchored `glide_duration`** — 40 hours is
  `1970-01-02 16:00:00`. Slice off the date and 40h is indistinguishable from 16h.
- **`cmn_schedule` inherits `business_calendar`** (Australia): `label`/`plural_label`/
  `calendar_name` carry mandatory flags that OOB rows nonetheless leave empty.
- **Dynamic CI Group is `cmdb_ci_query_based_service`** (not `cmdb_ci_group_dynamic`, which does
  not exist). CSDM membership for Application Services goes through **`svc_ci_assoc`**, not
  `cmdb_rel_ci`.
- **Foundation order is load-bearing:** company → business unit → department (roots first) →
  locations (parents first) → users → groups → **schedules BEFORE SLAs**.
- **`kb_knowledge` inserted over REST lands in `workflow_state=draft`** — publishing is a separate
  transition, not a side effect. Say *authored*, never *published*, unless you verified the state.
- **When auto-selecting a choice value, rank by intent, never alphabetically.** A `sorted()[0]`
  fallback silently picked a daily rotation over a weekly one purely because `d < w`.

### Verify-at-wire-time list

Open questions. Each one is something we do not know, written down so nobody assumes an answer.

1. **Reference-typed data pills across the custom-Action boundary** — broken in SDK 4.9.2 in both
   directions; the string-mirror workaround is load-bearing until proven otherwise. Whether this
   is an SDK emission bug or a Flow-runtime behaviour is UNDETERMINED. Re-test on the next bump.
2. **Flow trigger reads of a new same-project table** (the `lookUpRecord` workaround) — plausibly
   the same root cause as #1. Re-test together.
3. **`use_dynamic_default` blank in Service Portal** — authoring gap, portal-widget limitation, or
   instance setting? Determine before a user sees a blank field on a real form.
4. **`--include-data` root cause.** Rows inserted via REST after install are never registered as
   the application's own data, so the flag captures nothing and publish still reports success.
   UNCONFIRMED whether the real lane is a Fluent data-seed mechanism or a Studio-side step. Until
   answered, **count data rows in `sys_update_xml` after every publish.**
5. **`sysauto_script` execution on a PDI — RESOLVED 2026-08-09, and the answer splits the lane.**
   **Periodic jobs DO fire.** A `run_type=periodically` job (15 min) installed via the SDK executed
   at its scheduled second — marker `2026-08-10 02:30:01` UTC, `source=*** Script`, zero ATF runs in
   the window, and `sys_trigger.next_action` advanced 02:30 → 02:45. So the 2026-08-05 failure was
   **not** "PDIs restrict scheduled execution"; it is specific to the **on-demand Run Once**
   (`trigger_type=0`) path, which remains unexplained and unusable. **Law: schedule it periodically
   and read the log; never queue a one-shot trigger and expect it to run.** The escalation lane for
   things REST refuses is therefore alive, but only in its recurring form.
6. **Does a cheap model tier stay good on a HARDER problem?** One data point exists, on a
   moderate enhancement. Before making a cheap tier the default, run a deliberately nastier
   ticket — brownfield-shaped, ambiguous, or an integration.
7. **Instance reclamation policy** — primary-source the current rule before depending on an
   instance surviving a quiet period.
8. **OAuth / API-key auth lane** — untested. Basic auth plus the allow-list role works; do this
   before any multi-user agent setup.
9. **CSDM Business Application ↔ Application Service relationship verb** — the whitepaper has
   documented errata. Confirm before relying on this specific claim.
